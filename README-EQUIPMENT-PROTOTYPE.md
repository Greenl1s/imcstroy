# Удалённые приборы и отдельный прототип учёта оборудования

В архиве только изменённые и новые файлы, с путями относительно корня проекта.

## Что изменилось

- Удаление приборов теперь обратимое. Карточка остаётся в базе, а папка с файлами переносится в `База данных/Оборудование/Удаленные`.
- Для восстановления администратор открывает папку удалённого прибора в ИСУ и нажимает **Восстановить прибор**. Сохраняются идентификатор, параметры, история, фото, свидетельство, эталоны распознавания и связи с комплектами. Списанный прибор после восстановления остаётся списанным.
- Приборы на руках, частично выданные приборы, бронь и ожидающие передачи нельзя удалить до возврата/отмены брони.
- Удалённые приборы скрыты из рабочего списка, комплектов и результатов распознавания. Папка `Удаленные` не относится к обычной корзине и не очищается автоматически.
- Отдельный интерфейс: **https://files.imcstroy.ru/instruments-prototype/**. Его файлы лежат в `web-prototype/`; текущий интерфейс остаётся в `web/`.
- Оба интерфейса используют одну базу и один API. Пользователи, приборы, наличие, изменения карточек, выдача, возврат и удаление общие. Изменения из другого окна видны после обновления страницы; обновление в реальном времени здесь не добавлялось.
- В прототипе перед выдачей выбирается текущий проект ИСУ: можно искать по названию. Это работает для одиночной, массовой выдачи, комплектов и выдачи из брони. В списке только проекты, доступные пользователю; архивные, отменённые и удалённые проекты не предлагаются. Название проекта видно в месте использования, идентификатор сохраняется в базе и название фиксируется в истории выдачи.
- При наличии нескольких одинаковых вспомогательных приборов один пользователь может одновременно брать их по одной карточке для одного проекта. Для смены проекта нужно сначала вернуть ранее взятое количество.

## Обновление сервера

Загрузите файлы в GitHub с сохранением их путей. В `web-prototype` необходимо загрузить **всю новую папку**, а не только index.html.

**Внимание к docker-compose.yml:** единственное нужное изменение — строка в `services.caddy.volumes`:

```yaml
      - ./web-prototype:/srv/prototype:ro
```

Сохраните существующие серверные настройки, в частности переменные Planfix. Не заменяйте их содержимое содержимым примера. `.env` менять не нужно.

В терминале SSH перейдите в существующую папку проекта, где находится docker-compose.yml. Если на сервере остались локальные настройки compose, сохраните их перед pull:

```sh
mkdir -p "$HOME/backups/imcstroy"
cp docker-compose.yml "$HOME/backups/imcstroy/docker-compose-before-prototype-$(date +%F-%H%M).yml"
git status --short
```

Если `git status` показывает `M docker-compose.yml`, выполните:

```sh
git stash push -m "Server compose settings before equipment prototype" -- docker-compose.yml
git pull --ff-only
git stash pop
git diff -- docker-compose.yml
```

Если локальных изменений compose нет, достаточно `git pull --ff-only`. При конфликте stash остановитесь и разберите конфликт; не запускайте сервисы с маркерами конфликта.

До миграций сделайте свежую копию базы. Команда не печатает пароль:

```sh
DB_COPY="$HOME/backups/imcstroy/db-before-prototype-$(date +%F-%H%M).sql"
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > "$DB_COPY"
test -s "$DB_COPY" && ls -lh "$DB_COPY"
```

Продолжайте только после успешного завершения pg_dump. Убедитесь, что у вас также есть резервная копия `filemanager-data`.

Примените две миграции **по порядку**, до запуска обновлённого API и ИСУ. Каждая команда одной строкой:

```sh
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < db/043_instrument_deleted.sql
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < db/044_equipment_issue_projects.sql
docker compose config --quiet
docker compose build api filemanager
docker compose up -d --no-deps api filemanager
docker compose up -d --no-deps --force-recreate caddy
docker compose ps api filemanager caddy
docker compose logs --tail=40 api filemanager caddy
```

При любой ошибке миграции не переходите к следующему шагу. Пересоздание Caddy требуется, чтобы подключить новый том со статическими файлами; оно кратковременно прервёт доступ к сайту. Recognition AI пересобирать не нужно.

## Проверка после установки

1. Откройте основной учёт и прототип. В них должны быть одинаковые приборы и аккаунт. В прототипе сверху видна надпись о реальном наличии.
2. Для проверки восстановления используйте отдельную ненужную карточку: создайте её, добавьте фото, удалите через форму. В ИСУ откройте `База данных → Оборудование → Удаленные → папка прибора`, нажмите **Восстановить прибор**. Проверьте карточку и фото. Не удаляйте рабочий прибор ради теста.
3. При фактической выдаче выберите проект в прототипе. Обновите основной учёт: прибор должен числиться выданным, с названием проекта в месте использования. После фактического возврата верните его в любом интерфейсе и обновите второй.
4. Проверьте обычного сотрудника: доступные ему проекты видны, восстановление недоступно. При пустом списке проверьте в ИСУ доступ к разделу дел и к папкам проектов.
5. Если интерфейс старый, обновите страницу с очисткой кэша (`Ctrl+F5` на компьютере).

При сбое переноса папки карточка остаётся в базе. Открытие корня «Оборудование» повторяет синхронизацию; ошибки записываются в лог filemanager. Если имя папки занято, существующие файлы не перезаписываются — восстановленная папка получает суффикс.

**Старые удаления:** карточки, уже физически удалённые прежней версией, автоматически не восстановятся. Их оставшиеся файлы сохраняются в «Архиве». Для восстановления прежней карточки понадобятся данные из резервной копии.

## Выполненные проверки

- Проверен синтаксис изменённых JavaScript-файлов и всех модулей прототипа.
- Выполнены 24 существующие проверки прав, путей и адресов API, проверка действующей поверки перед выдачей.
- Выполнены новые проверки удаления/восстановления с реальными временными папками и файлами: ссылки на фото, поверку и эталоны, конфликт имён, повторная синхронизация, откат после ошибки записи путей в базу, защита удалённых папок, запрет удаления занятого/забронированного прибора и проверка прав на проекты.
- В Chrome проверены интерфейс прототипа, поиск проекта, отмена через Escape, выдача с привязкой к проекту и общий остаток/возврат между двумя интерфейсами. Ответы API в этих тестах имитировались, реальные серверные данные не изменялись.
- PostgreSQL-миграции и запуск Docker на вашем сервере локально не выполнялись: их окончательная проверка — команды установки и проверка после установки выше.

Новые локальные проверки: `node tests/equipment-trash-prototype.cjs`.
